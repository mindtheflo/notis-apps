What broke, what is fixed

Open Sandbox

The GitHub CLI is installed but signed out

gh 2.97.0 is on PATH and .gitconfig already routes GitHub credentials through 'gh auth git-credential', but 'gh auth status' reports no logged-in host and no GH_TOKEN or GITHUB_TOKEN is present in the sandbox environment. Every clone, push and pull request in this feature depends on that credential, so setup could not have worked as assumed.

FixThe repository skill runs the GitHub device flow directly against github.com/login/device/code with the GitHub CLI's own public client id, shows the user the one-time code, polls for the grant, then pipes the token into 'gh auth login --with-token'. That is scriptable without a TTY, which 'gh auth login --web' is not.
Open Sandbox

The sandbox ships Python 3.9 but the notis bootstrap needs 3.12

/usr/bin/python3 is 3.9.25 and there is no python3.12 on PATH, while setup.sh opens with 'python3.12 -m venv server/.venv'. Repository setup would fail on its first line.

FixThe image is Amazon Linux 2023 with passwordless root sudo and python3.12 available in the default repository, so the skill installs the interpreter as a prerequisite step before running the repository's own bootstrap script.
Open Sandbox

Repository setup outlives the per-command timeout

Sandbox commands are capped at twelve minutes. A cold notis setup is a pip install plus six or more npm installs on two vCPUs, which is well past that, so a foreground run is guaranteed to be killed part way through and leave a half-installed tree.

FixLong steps run detached with nohup against a log file and a status marker, and the skill polls the marker. That also survives the agent's own turn ending.
Fixed Design

The notis repository has no install.sh

The requested skill contract names install.sh, dev.sh and archive.sh. This repository's bootstrap script is setup.sh; dev.sh and archive.sh do exist. Hard-coding the three names would either fail here or force a rename of a script the whole team uses.

FixEach repository row stores its own setup, dev and archive commands. The skill discovers an existing bootstrap script and records it; it only writes new scripts when a repository genuinely has none.
Fixed Skills

The executable bit does not survive bundle transport

Scripts arrive in the sandbox without the executable bit, so the first run died with 'Permission denied' when one script called another. The skill instructions already told the agent to use 'bash <path>', but the scripts were calling each other directly.

FixEvery internal script-to-script call names its interpreter. The packaging step still sets the bit for anyone reading the bundle on disk, but nothing depends on it.
Platform gap Platform

App-declared skills cannot carry their scripts

notis.config.ts can declare skills from the app source tree, which is the right packaging model, but only the entrypoint's markdown is read. Both of these skills are a few hundred lines of shell and Python and cannot be inlined.

FixSkills are packaged and published separately, then attached to the app through bundled_skill_ids. Verified: the full bundle including scripts/ materialises under /vercel/sandbox/.notis/skills/<name>/ through the normal sync path.
Fixed Tooling

A local dev backend gives the sandbox an unreachable API base

The sandbox received NOTIS_API_BASE=http://localhost:3001 from the local server, so its CLI could not call home and every row write from inside the sandbox failed with a network error.

FixSandbox commands in this build pass the user's real service origin explicitly. Recorded in the wishlist: the resolver should not inject a loopback address into a remote sandbox.
Fixed Tooling

apps verify refuses to run without Store screenshots

Verify is the render check, but it fails on listing metadata before it renders anything. Scaffolding from notis-database also left that app's five screenshots behind, so the first failure was about alt text for another app's gallery.

FixStale scaffold assets removed, four screenshots declared and generated from fixtures. Both routes now verify clean.
Fixed Platform

An absolute path in any row property made every CLI write fail

Writing a row whose text property held an absolute path returned 503 file_target_schema_unavailable. Any value starting with a slash is read as a raw local file reference, which forces a provider file-upload schema lookup; a generated row-write tool has no such schema and never will, so the failure was permanent while the message invited a retry. This app stores checkout and secrets paths, so nothing could be recorded at all. It affects any Notis database holding a path.

FixThe raw-reference heuristic now skips generated row-write tools, which declare no file-uploadable argument. Provider tools still fail closed, so passing a local path as a Dropbox file body is still refused. Extracted as a named predicate with unit tests covering both directions, and verified live: the same write that returned 503 now succeeds.
Fixed Sandbox

The sandbox image has no /dev/fd, so bash process substitution fails

Every 'while read ... < <(command)' died with '/dev/fd/63: No such file or directory'. /proc/self/fd exists but /dev/fd does not, so the shell cannot open the substituted stream. Any script written on a normal Linux or macOS box will hit this.

FixThe three loops that used process substitution write to a temp file and read from it, which is portable and keeps the loop in the calling shell so its counters survive.
Fixed Secrets

Env files copied into a workspace showed up as untracked

Creating a workspace copies the repository's env files into the new tree. For a repository that does not already ignore them, they appear in git status, which is one careless 'git add -A' away from committing a secret. Warning about it in the skill instructions is not a guarantee.

FixApplying secrets also appends each file to the repository's info/exclude, which is per-checkout and never committed, so it works even for repositories whose .gitignore we do not control. First attempt wrote to the worktree gitdir, where git does not read it; corrected to the common dir. The tree now reports clean with the env file in place.
Fixed Tooling

The worktree CLI credential expires after an hour

Mid-build every local CLI call started returning auth_expired for the worktree profile, which reads as missing data: a database query returned zero rows for a database that demonstrably had rows. Sandbox-side calls were unaffected because the sandbox mints its own token per command, so the two surfaces disagreed about the same data.

FixRestarting the dev session mints a fresh credential. Worth knowing before diagnosing an empty query as a data problem. --refresh-portal-entry-link does not refresh it; only a restart does.
Fixed Workspaces

Pull request status never appeared, because the lookup used a flag that does not exist

Sync called 'gh pr view --repo <url> --head <branch>'. gh pr view has no --head flag -- that belongs to gh pr list -- so the command failed on every call. The failure was swallowed by 2>/dev/null and reported as 'this workspace has no pull request', which is exactly what a workspace without one looks like. An open pull request stayed invisible in the app.

FixSync runs 'gh pr view' from inside the worktree with no selector, which resolves the pull request for the checked-out branch. Verified against a real one: the row now reads Open with its number, URL and check rollup.
Fixed Secrets

Staging an upload that is already the secrets directory failed

Uploading environment files straight into the secrets directory and then recording them made cp copy each file onto itself, which is an error. The files were already exactly where they belonged.

FixThe install step compares resolved paths and, when they are the same directory, records the files without copying.
Fixed Tooling

A full-table read exceeded the CLI's default request deadline

A repository sync failed with network_timeout after 30 seconds. The read was slow, not broken, but the caller could not tell those apart.

FixThe row helper sets a 90 second request deadline on every tool call.
Platform gap Platform

The development runtime gives an app its own empty copies of its databases

Declaring databases in notis.config.ts makes the hidden workspaces-dev runtime app materialise its own repositories and workspaces databases, separate from the installed app's. Two consequences. Slug lookup from outside the app runtime became ambiguous, which is how the skills address databases, and it started failing with 'Several databases use the slug repositories'. And the app mounted under Local development reads the dev app's copies, which are empty, so it shows first-run onboarding rather than the real rows a skill just wrote.

FixThe row helper resolves by listing databases and choosing the one owned by the installed app, preferring the copy that holds rows, so a stale empty twin can never win. The app showing real data in the portal still needs a deploy: that is what binds the bundle to the installed app and its databases.
Open Tooling

apps verify --mode live reported success on a route that failed to load

Live verify passed both routes. A screenshot of the same live run shows 'Could not load workspaces -- Runtime request failed: Route not found'. Verify's criterion is that nothing throws during render, and a well-behaved error state satisfies that, so an app that handles failure gracefully is indistinguishable from one that works. The underlying error is expected: the app has never been deployed, so the manifest carries no routes and runtime_query cannot resolve one.

FixNot fixed. Recorded in the wishlist: live verify should assert that declared databases actually returned data, otherwise it grades error handling rather than the app.
Fixed Secrets

The skill told the user to send env files through chat, which publishes them

The repository skill originally said to ask the user to send the repository's env files as an upload. A file attached to a conversation goes through FileHandler.upload_to_supabase, which writes to the 'attachments' bucket -- public -- and returns a permanent unsigned public URL. Following that instruction with a production .env would have published every key in it. It was never executed: the files in this run were written straight into the secrets directory, so nothing reached storage.

FixThe skill now forbids routing an env file through a chat attachment or any tool that mints a durable URL, and instead has the user place the files directly in the secrets directory. secrets-install accepts that directory as its own source.
Fixed Platform

An app can now write a file into the cloud computer, and only write

upload_sandbox_file insisted on an http URL, which meant any file had to be published before it could be delivered. Views were also barred from every sandbox tool, so an app could not deliver one at all. Both were reasonable defaults and together they left credentials with no safe route.

FixThe tool accepts content as base64 or utf-8 alongside url, plus an optional mode. VIEW_FORBIDDEN_TOOL_NAMES subtracts this one name, and the shell-mode gate gains a portal-view door that only the upload path opens. Proven against the running server: upload returns 200 with a matching sha256 and the file lands at 0600, while list and download both return 403.
Fixed Skills

A project's own dev script hijacked our CLI calls

Step 7 runs the repository's dev script to prove it works. The notis repo writes .context/notis-routing.json, a worktree CLI lease, so every later Notis CLI call made from inside that checkout failed with dev_runtime_unavailable. The skill caused this itself and it recurs for any project shipping similar tooling.

FixThe row helper runs the CLI from /vercel/sandbox, outside any checkout, so a lease belonging to the project under test can never capture our calls. The skill also warns about it for hand-run commands.
Fixed Skills

Workspace creation fell back to a branch called main

With no repository row, workspace.sh defaulted the base to 'main' and failed with 'fatal: invalid reference: origin/main' on a repository whose default is beta. The error reads like a git problem rather than a missing row.

FixThe base is resolved from git (symbolic-ref refs/remotes/origin/HEAD) when the row has none, so the fallback is the repository's real default.
Fixed Skills

A hand-rolled gh pr create left the app blind

The agent opened a real pull request with gh directly instead of workspace.sh pr, so nothing synced and the row kept reporting no pull request while #1873 was open. It then tried to repair the row by hand rather than syncing.

FixThe skill now says to use workspace.sh pr rather than gh, and that sync is the repair tool for a stale row.
Fixed Tooling

Republishing the skills forked duplicates

publish-skills.sh always called CREATE_SKILL, so each run made a second skill with the same name. Both then materialised in the sandbox and an agent would read whichever copy it found first.

FixThe script looks the skill up by name and updates in place, creating only when none exists. The two duplicates it made were deleted.
Open Process

Editing the tree while a live test ran killed four turns

The dev stack runs with --reload-backend. Saving a server file mid-run reloaded the backend and killed the in-flight conversation turn; four interactions died that way and one inbound message was dropped before it became an interaction. The repo's own guidance says to sequence edits into quiet windows, and this run did not.

FixNot a code fix. Either stop editing while a live conversation test is running, or run the validation against a stack started without --reload-backend.
Fixed Platform

The per-surface shell re-cut turned the app from a board into a product

run_sandbox_shell is now exposed to views and run_desktop_shell is text-only, which is the right split: a desktop shell reachable from a third-party bundle would be a pivot onto the user's own machine. Before this the app could only display rows a skill had written.

FixThe app declares run_sandbox_shell and drives the skills' own scripts. GitHub sign-in is a real control that reads gh auth status, starts the device flow and shows the code; every repository and workspace has a Sync that runs the same sync a skill runs. There is no second implementation to drift.
Open Tooling

A caller cannot override an injected session variable

run_sandbox_shell accepts an env argument, but the executor merges it as {**command_env, **sandbox_env}, so the session environment wins. That precedence is correct -- otherwise an app could replace NOTIS_JWT and act as someone else -- but the argument silently does nothing for any variable the session already sets, NOTIS_API_BASE among them.

FixNot a code change. Documented in the wishlist so nobody spends an afternoon on it. It is also why an app-driven sync cannot be exercised against a local dev backend: the sandbox is handed localhost:3001 and no caller can point it elsewhere.

What the apps SDK should have given me

Tools

Row-write tool names are content hashes

What it costCreating a database returns a write tool named LOCAL_NOTIS_DATABASE_UPSERT_REPOSITO_3AD526820B9519B6E71F. The slug is truncated and a twenty-character hash is appended, so the name cannot be predicted from the slug, cannot be written into notis.config.ts before the database exists, and cannot be hard-coded in a skill that is meant to work for any installer of the app.

What would fix itA stable, derivable write tool name per database slug, or a generic write tool that takes the slug as an argument the way LOCAL_NOTIS_DATABASE_QUERY already does.

Runtime

An app cannot start work, only display it

What it costEverything this product actually does is a shell action on the cloud computer: clone, worktree, setup, push, open a pull request. An app is a React bundle whose only outward call is a declared tool, so the buttons that would make this a product cannot exist. The user has to go to a chat surface and ask, then come back to the app to see the result.

What would fix itA way for an app to hand work to an agent: a hook that starts a skill or an agent task with arguments and returns a handle the UI can follow to completion.

Runtime

No change feed, so state has to be polled

What it costWorkspace state moves while nobody is looking at the app: a setup finishes, checks go green, a pull request merges. The runtime bridge is request/response over fetch, so the only options are a manual refresh or an interval that spends tool calls on rows that mostly have not changed.

What would fix itA subscription hook over an app-owned database, so a row written by a skill on the sandbox reaches an open app view without polling.

Schema

No secret-shaped property

What it costA repository's environment files are the most sensitive thing this app touches. There is no property type that means 'this exists and is valid but must never be rendered or returned in full', so the schema stores a status and a file list and deliberately keeps the values out of the database entirely.

What would fix itA secret property type that stores a reference plus metadata, is redacted in every query response by default, and can be resolved only by a shell action running as that user.

Runtime

An app cannot see the cloud computer

What it costThe first onboarding step is signing the GitHub CLI in, and the app has no way to ask whether that already happened. Nothing writes it to a database and an app cannot run a command to check.

What would fix itA read-only capability for a few cloud computer facts behind the same install-time prompt that workspaceDatabases: 'read' already uses.

Packaging

Declared skills should be able to point at a directory

What it costAn app can declare a skill from its own source tree, but only as one markdown file, so a skill with scripts has to be published out of band and attached by id. The app source stops being the complete source of the product.

What would fix itAccept a directory path in skills[].path and package it during apps build the way the source snapshot is already packaged.

skills: [{ key: 'new-workspace', path: './skills/new-workspace/', name: 'New workspace' }]
Errors

A permanent failure should not be described as retryable

What it costThe 503 on every row write said 'Retry after tool discovery recovers.' Nothing was recovering: generated tools have no provider file-upload schema, so the condition was permanent. That wording sent the first debugging pass toward a transient-outage theory before the real cause showed up.

What would fix itDistinguish 'this schema is temporarily unresolvable' from 'this tool has no such schema'. Only the first is a retry.

Sandbox

Document what the sandbox image does not have

What it costThree separate stops came from image assumptions: Python is 3.9 not 3.12, /dev/fd does not exist so process substitution fails, and the GitHub CLI is installed but signed out. Each was only discoverable by running into it.

What would fix itA short, maintained note on the sandbox baseline: interpreter versions, shell features that are absent, which CLIs ship and what state they ship in.

Tooling

Live verify should distinguish a working route from a graceful failure

What it costLive verify passed two routes that were both rendering an error state. Building an app that fails politely is good practice and it made the check meaningless, so the failure was only caught by looking at a screenshot.

What would fix itIn live mode, assert that each declared database returned at least one successful response, and fail the route when every runtime call errored.

Runtime

Local development should be able to read the installed app's data

What it costThe development runtime materialises its own empty databases, so the app under Local development shows first-run onboarding while the installed app holds the real rows. Iterating on a view of live data means deploying, which is exactly the step the workflow says to avoid until the user has tested locally.

What would fix itAn opt-in that points a dev session at the installed app's databases, so local iteration can be done against real data without deploying.

Secrets

There was no safe way to hand a credential file to the cloud computer (built)

What it costEvery agent-driven route from a user's machine to the sandbox goes through a durable URL in the public attachments bucket. For a screenshot that is fine. For a .env it means publishing production keys at a permanent address, so the only correct advice is that the agent must not carry the file at all -- which leaves the user doing it by hand.

What would fix itBuilt. upload_sandbox_file now accepts inline content and an optional mode, and views may call that one tool. The Repositories view sends environment files straight from the browser to the sandbox at 0600, with no URL and nothing stored.

SDK

A job primitive to go with shell access

What it costA shell call is one request/response, so anything genuinely long -- a clone, a dependency install, a test run -- has to be started detached and polled. Every app that touches the cloud computer will now reimplement that.

What would fix itstart, status, tail and wait in the SDK. It is the same shape as the job.sh this app's skills already ship.
